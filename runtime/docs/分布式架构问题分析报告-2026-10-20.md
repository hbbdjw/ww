## 0. 架构分层与一致性模型（判断严重级别的前提）

- **控制面真源 = 单个共享 PostgreSQL**：节点注册表、leader 单行租约、放置表、迁移任务、能力状态、怀疑票、LB 配置全部落同一库。不自建 Raft/Paxos，把共识整体下沉到 DB。
- **决策中心化、执行分布式**：DB 单行租约选出唯一 leader（`ReconcileLoop`）做放置/治愈/重平衡/排空决策；迁移执行由各节点 `MigrationEngine` 以状态机 CAS + epoch fencing 并发推进。
- **数据面写权限三重 fencing**：放置 epoch（CAS）+ `valid_after_ms`（新主等旧主租约到期 + 1s）+ 本地分区写租约（fail-closed）。与控制面 leader 身份解耦。
- **对外一致性（实际实现）**：读写均路由属主 → 单属主视角 read-after-write 强一致；副本异步补齐、对账收敛为最终一致；持久性承诺默认半同步（至少一副本 ack 才应答，2026-10-20 起默认开启；超时降级 + at-risk 观测，可配 fail-closed）。

关键推论：数据面有独立 fencing，控制面的多数问题是「不一致/不可用」而非直接丢数据；但 fencing 的**时钟锚定**与**迁移期的写窗口**是两处真实的数据安全缺口。

## 1. P0 — 致命（会丢已确认数据 / 数据面脑裂）

### P0-1　扩容重平衡期间源端不冻结 + 位置型 checkpoint → 已 ack 写入静默丢失并被清源抹除　【✅ 2026-10-20 已修复，见上文实施记录】
**位置**：
- `runtime/scheduler/.../ReconcileLoop.java` `healOrRebalance`（扩容重平衡分支 ~879-911：直接 `migrateInBatches`，**全程无 freeze**；对比 `drainNodes:678` 有 freeze）
- `runtime/migration/.../MigrationEngine.java` `copyRemaining`/`syncUntilQuiescent`（checkpoint = 已迁对象**计数**）
- `runtime/data/.../storage/StorageCapability.java:628-662` `exportPartition(partition, skipObjects)` / `PartitionExportIterator.nextMatchingObject`（按**当前字典序位置**跳过前 N 个对象）

**为什么是问题（两个独立分析同时命中，从不同角度）**：迁移的断点续跑与「SYNCING 静默收敛」判定建立在「对象集合字典序位置偏移」上，源端并发写时这不是稳定游标。
- 游标错位场景：分区 `{a,b,c}`，COPYING 迁完 a、b（checkpoint=2）；客户端 PUT 新对象 `ab`（字典序在 b、c 之间，已 ack，源仍是 PRIMARY，fencing 通过）；SYNCING 从 checkpoint=2 导出 → 跳过 `{a,b,ab}` 前 2 个后导出 `{c}` → **`ab` 永不被导出**；cutover CAS 成功、`clearSourcePartition` 把源端（含 `ab`）整分区删除。`verifyCount` 只比计数，检测不到。
- cutover 窗口场景：SYNCING 判定「静默」后、cutover CAS 前，客户端向旧属主写入成功得 200；cutover + 清源后该写被销毁。旧属主本地视图刷新（≤500ms）与本地租约失效前仍可接受写。
- 放大：`CacheCapability.checkOwner(partition, -1L)` 与 `StorageCapability`（`:908`）的 `expectedEpoch=-1` 使 epoch 比对被旁路，仅剩 owner 身份 + 租约兜底，窗口无法完全闭合。remediation plan §3.18 已将其立项为 A2/7A 专项，**至今未落地**。

**级别**：**P0**。每次扩容重平衡都有毫秒~秒级窗口 × 被迁分区数；STORAGE 语义下是持久化数据丢失，且被清源后不可恢复。

**修复方向**：重平衡迁移对源分区在 cutover 前短暂 freeze（或网关转发携带真实 epoch、目标端启用比对）；把导出游标从「位置型」改为「键型」（记录 last exported key，按 key > cursor 续跑）；cutover 前二次静默校验 + 迁移完成确认携带持久化凭据后再清源。

### P0-2　本地写租约用 app 墙钟而非 DB `lease_until_ms` → 时钟偏移超 margin 即数据面双写（脑裂）　【✅ 2026-10-20 已修复，见上文实施记录】
**位置**：`runtime/server/.../placement/PartitionLeaseManager.java:204-211`（`renewOnce`）、`CachedPlacementView.checkWritable:168-194`、`JdbcPlacementStore.renewLeases:517-551`

**已核实**：`renewLeases` 已返回 DB 时钟计算的 `lease_until_ms`，但 `renewOnce` **丢弃返回值**，改用 `localExpiry = requestStart(app钟) + ttlMs - safetyMarginMs`（默认 margin 仅 1000ms）；`checkWritable` 又用 app 钟 `now` 比 DB 钟写入的 `valid_after_ms`。于是「旧属主停写」与「新属主起写」分别锚定在**两台主机的墙钟**上，不重叠性完全依赖 `app钟 ≈ DB钟`（误差 < margin）。

**故障时序**：旧属主主机时钟快于 DB 时钟 > margin（NTP 步进、VM 暂停恢复后跳变）→ 其 `localExpiry` 实际晚于 DB 租约到期 → 旧属主在 DB 租约已过期、新属主 `valid_after` 已到并开始写之后**仍认为本地租约有效继续接受写** → **同一分区新旧属主双写**。

**级别**：常态（偏移 <100ms）由 1s margin 覆盖，安全；一旦时钟异常超过 margin 即升级为 **P0 数据面脑裂**。定级 **P0（条件触发）**，因其后果是双写冲突且 fencing 体系的核心假设被打破。

**修复方向**：本地写门限直接用 `renewLeases` 返回的 DB `lease_until_ms`（减 margin），把 fencing 锚定在单一 DB 时钟上；margin 按环境时钟质量配置。

## 2. P1 — 严重（故障时不可用 / 数据不一致 / 架构级单点）

### P1-1　控制面 100% 依赖单个共享 PostgreSQL，无 HA/共识兜底　【⚠️ 文档化：控制面可用性 == DB 可用性，需运维侧 HA】
**位置**：`RuntimeAssembly.JdbcStoreConfiguration:765-808`、`JdbcLeaseStore`、`JdbcNodeRegistry`、`JdbcPlacementStore`；`runtime/docker-compose.yml` / `scale-out.sh`（单实例 `host.docker.internal:5432`，无副本/Patroni）
**问题**：DB 宕机 → ① leader 无法续约，TTL（默认 10s）后无 leader，调度/治愈/迁移全停；② 数据面 `PartitionLeaseManager` 续约失败，本地租约 TTL（默认 5s）后**全集群写路径 fail-closed**（读走 last-good 快照仍可用）；③ 心跳落库失败可能引发误判连锁。DB 异步复制 + 故障切换发生 split-brain/回滚时，runtime 无第二道防线，会把 DB 级不一致放大成集群级（旧 leader 租约行「复活」→ 双 leader）。注册/放置/租约/任务/RBAC/日志同库互相放大。
**级别**：**P1**（架构级单点；文档未把「DB 高可用」列为前置要求）。
**修复方向**：文档化「控制面可用性 == DB 可用性」；中期 PG 流复制 + 受控 failover；注册/租约与业务日志分库降压。

### P1-2　leader 无 fencing token + 无后台续约 → 长周期双 leader 并发改元数据　【✅ 2026-10-20 已修复】
**位置**：`ReconcileLoop.runOnce:324-362`、`stillLeader:986-993`、`loop:415-427`（类注释 `:85-88` 自认「无 fencing token、无后台续约线程」）
**问题**：租约仅在周期开始和批间（`migrateInBatches:968`、`fanoutCommands:922`）续约。`stillLeader()` 只覆盖 `drainNodes`/`healOrRebalance` 的长迁移后，**不覆盖** `bootstrapPlacement`、`replaceAll`、`reassignReplicasBatch`、`setActual`、`promoteConfirmedDead`、`sweepStaleJoining`、`decommission.advance`、`compensateStaleFreezes`。某次 reconcile 因能力多 / `topUpReplicas` 改 256 分区 / 命令各 5s deadline 而耗时 > TTL(10s)，租约中途过期，L2 接管；L1 仍在同一 `runOnce` 内继续执行——例如缩容排空 `placementStore.replaceAll(capability, List.of())`（`drainNodes:684`）**清空整能力放置表**，而 L2 刚 bootstrap 出环 → 环被抹掉，数据面属主 `checkWritable` 读空行 → 全部 `StaleEpochException`、写不可用。`cutover/promote` 有 epoch CAS 兜底（安全），但 `replaceAll`/`reassignReplicas`/`setActual`/freeze-stop 命令**无 leader epoch 保护**。
**级别**：**P1**（损害上界是短暂写拒绝/环清空，非数据错乱，因数据面有独立 fencing；但控制面可用性受威胁）。
**修复方向**：租约行携带单调 `leader_epoch`，所有控制面写 SQL 加 `WHERE leader_epoch=?`；每个副作用阶段前 `stillLeader()` 复核；引入可注入调度的后台续约线程（保持 TestClock 兼容）。

### P1-3　默认异步复制 + promote 不校验副本新鲜度 → 主死即丢已 ack 写　【✅ 已修复（半同步默认开 + 排空屏障；死主窗口残余可观测）】
**位置**：`runtime/data/.../storage/engine/StorageProperties.java`（`semiSyncEnabled=false`、`semiSyncFailClosed=false` 默认）；`StorageReplicator.replicateSync`（只等**首个** ack，非多数派）；`ReconcileLoop.tryPromoteLiveReplica`/`tryPromoteDrainTarget`（提升前**不比对副本滞后量**）
**问题**：主落盘 v5 并 ack，异步复制未完成（或失败入内存 backlog）时主崩溃；leader 越过宽限期 `promoteReplica` 提升停在 v4 的副本 → v5 永久丢失。计划内 drain 同样中招：`freeze(true)` 只停新写，**不等待在途虚拟线程复制与 backlog 清空**就提升/停机（`StorageReplicator.stop()` 明确「不清空 backlog」）。半同步即便开启，RF=3 时「1 ack + 主」也非多数派，且默认降级放行（at-risk 仅记日志）。backlog 仅内存，重启即失。
**级别**：**P1**（有 at-risk 观测与文档化承认；若对外承诺「ack 即不丢」应升 P0）。
**修复方向**：生产默认开启半同步并考虑 fail-closed；promote 前比对副本滞后；drain 停机前等待 backlog 排空。

### P1-4　副本删除无版本护栏 + backlog 乱序重放 → 新写入被过期删除意图抹掉　【✅ 2026-10-20 已修复】
**位置**：`StorageReplicator.afterDelete`/`replayBacklog`（delete 分支直接 `client.replicateDelete`，不重读本地状态——对比 PUT 分支有 `replicateOrTombstone` 重读）；`StorageReplicationClient.replicateDelete(node,bucket,key)`（协议**不携带 version**）；`StorageCapability.replicaDelete` / `ObjectStore.delete`（无条件删）
**故障时序**：t1 DELETE v5 → 对副本 A 的 replicateDelete 失败入 backlog；t2 PUT v6 → 对 A 复制**成功**（不入 backlog，去重只在「新条目也失败入队」时覆盖旧 delete 条目，此处 put 成功故 delete 条目残留）；t3 backlog 重放 → 向 A 发无版本 delete → **A 上 v6 被删**。A 分叉直到下轮对账（默认 5min）；期间 A 被提升则 v6 永久丢失。不经 backlog 也有同类竞态：afterDelete 与 afterPut 两个虚拟线程无序，delete RPC 后到即覆盖。
**级别**：**P1**。
**修复方向**：replicateDelete 携带 version，副本端做版本护栏（仅当 version ≥ 本地才删）；backlog 重放前重读本地状态。

### P1-5　反熵只修「副本缺/旧」不修「副本多」→ 已删对象在副本永久复活　【✅ 2026-10-20 已修复】
**位置**：`StorageReplicator.reconcile()`（只遍历**本机为主**的现存对象，对 `s==null || s.version<local` 补推）；删除意图仅存内存 backlog（`stop()` 注释自认「由对账兜底」，但对账恰恰不兜删除）
**故障场景**：主删 v3，replicateDelete 对副本 B 失败入 backlog；B 长期不可达期间**主节点重启**（backlog 蒸发）；B 恢复后仍持有 v3，对账永不发现（主端已无该对象，不在扫描范围）。读/list 被属主口径掩盖（gateway T20），但 B 一旦 promote → **已删除对象复活**（违反删除语义），迁移导出会把僵尸对象搬走。
**级别**：**P1**（需「删除复制失败 + 主重启」叠加，但后果永久）。
**修复方向**：对账覆盖「副本多余对象」（删除意图持久化为墓碑，或周期比对副本键集差集）。

### P1-6　version 为节点本地计数、非全局唯一 → failover 后同版本异内容，对账只比 version 不比 etag，分叉不可修复　【✅ 对账比 etag + 主端权威覆盖；全局版本方案仍为后续项】
**位置**：`ObjectStore.putPrimary`（`newVersion = existing.version + 1`，仅基于本地 meta）；`ObjectStore.putReplica`（T26：同 version 异 etag「保留先到」仅计数告警）；`StorageReplicator.isReplicaLagging`（`s.version() < local.getVersion()`——**版本相等即视为一致，不比 etag**，尽管摘要里有 etag 字段）
**故障时序**：主 M ack 了 v4（内容 X）后死亡，副本 A 停在 v3、副本 B 恰好收到过 v4(X)；提升 A 为新主，新写产生 v4'(内容 Y)；B 持有 v4(X)。对账：新主 A 看 B `version 4 == 4` → 不落后 → **永不修复**。此后 B 被提升则 X 复活、Y 丢失——历史分叉取决于故障顺序，不可预测。
**级别**：**P1**（与 P1-4/P1-5 叠加分叉面更大）。
**修复方向**：version 带 node/epoch 前缀（如 `epoch<<32|seq`）保证全局唯一；对账比对 etag。

### P1-7　迁移 clearPartition 后旧源 backlog 重放把陈旧 PUT 翻转为 replicateDelete 且无属主校验 → 误删新主的副本数据　【✅ 2026-10-20 已修复】
**位置**：`StorageReplicator.replayBacklog`（重放前只查 `isServing(node)`，**不查本机是否仍拥有该分区 PRIMARY 身份**）+ `replicateOrTombstone`（本地对象没了就发墓碑删除）；`MigrationEngine.clearSourcePartition`
**故障时序**：分区 P 从 S 迁到 T（rebalance，S 存活、复制器继续跑）；S 的 backlog 残留 P 的某 put 条目（此前对副本 C 失败）；cutover 后 `clearPartition` 清掉 S 上 P 全部对象；backlog 重放 → `replicateOrTombstone` 发现本地无对象 → 向 C 发 `replicateDelete` → **C 上该 key 现行副本（可能已是新主 T 写的新版本）被删**。T 的对账最迟 5min 后修复，期间 C 被提升则丢数据。
**级别**：**P1**。
**修复方向**：backlog 重放前校验本机仍持该分区 PRIMARY 身份且 epoch 匹配。

### P1-8　默认单观察者判死（多数仲裁默认关闭）→ 非对称分区误杀健康节点　【✅ 2026-10-20 已修复（默认开启仲裁）】
**位置**：`runtime/server/.../RuntimeProperties.toMembershipConfig:369-375`（`suspicionQuorumEnabled` 默认 false → `localDeadWriteback=true`）；`MembershipService.transitionLocal:771-796`；`ReconcileLoop.promoteConfirmedDead:484-538`（多级仲裁已实现但默认关）
**故障时序**：5 节点，A→B 单向网络故障（B 健康、其余节点都能连通 B）。A 收不到 B 的 ack（`sendHeartbeat` 只在收到 ack 时 `recordSignal`），A 的 φ 判 B DEAD → **直写共享注册表 B=DEAD** → 所有节点经 `listAlive` 读到 B 已死 → B 被移出候选、其分区触发治愈/隔离。B 需靠自检（每 5 拍≈5s）`reRegister()` 复活。窗口内 B 的分区（默认 rf=1）被标 DEGRADED、网关拒流 → 健康分区被无谓阻断数十秒。
**级别**：**P1**。
**修复方向**：生产（≥3 节点）默认开启 `suspicionQuorumEnabled`，只有 leader 按多数票提升 DEAD。

### P1-9　放置完全无故障域（机架/主机/电源）感知　【✅ 2026-10-20 已修复（zone 反亲和，需配置 RUNTIME_NODE_ZONE 生效）】
**位置**：`runtime/placement/.../PlacementNode.java`（仅 `id + weight` 两字段）；`WeightedRendezvousHash.selectNodes`（纯分数 top-N，无反亲和约束）；`PlacementEngine.calculate`
**问题**：rf=2（compose 默认）时 PRIMARY 与 REPLICA 可能落在同机架/同主机/同电源域；整机架断电 → 该分区双副本同时丢失 → 走 DEGRADED 隔离（503）甚至 force-adopt 数据丢失。当前 4 容器同宿主机部署使该问题必然成立——宿主机即共同故障域，「副本」仅提供进程级冗余。
**级别**：真实多机部署 **P1**；当前单机 compose 形态 **P2**（结构性设计缺口）。
**修复方向**：`PlacementNode` 增加 rack/zone 维度，HRW 选副本时同域降权/排除。

## 3. P2 — 中等（边界场景 / 运维死锁 / 功能缺失）

### P2-1　全链路墙钟（非单调钟），NTP 步进可致误判死/延迟检死
**位置**：`runtime/common/.../SystemClock.java`（`System.currentTimeMillis()`）；`MembershipService.detectFailures:564-597`；`PhiAccrualFailureDetector.phiAt:122-137`
φ 计算、`lastHeard`、`deadSince`、各类 cooldown 全用墙钟。宿主机时钟向前跳 → `now-lastHeard` 瞬间变大 → φ 飙升 → 健康 peer 误判（叠加 P1-8 单观察者直写 = 全局误杀）；向后跳则延迟检测真死。`heartbeat()` 对 `interval<=0` 有不污染分布的保护，但判定侧读取的 `now` 仍是墙钟。
**修复**：故障检测/租约本地计时改用单调钟（`System.nanoTime` 派生），墙钟仅用于日志。

### P2-2　节点间 gRPC 明文无认证 → 可伪造自报心跳投毒成员视图 / 下发控制命令
**位置**：`MembershipService.sendHeartbeat:531-534`（`usePlaintext()`）、`fromProto:921-937`（信任 `node_id`）；`GrpcNodeCommandChannel.stubFor:178-181`（`usePlaintext()`）
`merge(reported, directFromSource=true)` 对「自报」恒采纳。任何能连到 membership gRPC 端口的一方发一条 `HeartbeatReq{self: NodeInfo(victimId, attackerHost, ACTIVE)}` 即被当作 victim 直证自报合并 → 可把 victim 的 host/port 指向攻击者劫持路由；ClusterControl 端口无认证可被下发 `freeze/stop`。HTTP 侧有 RBAC，节点间 gRPC 无 mTLS。
**修复**：集群内网 gRPC 启用 mTLS + 节点身份校验（`node_id` 绑定证书 SAN），`fromProto` 拒绝与连接身份不符的自报。

### P2-3　delete 先删 .meta 再删 .data，两步间崩溃 → 单 key 被「毒化」（读 500、写拒绝），无自动修复
**位置**：`ObjectStore.delete`（顺序注释自认与写入对称）、`ObjectStore.readMeta`（T15 隔离损坏 meta 为 `.corrupt`）、`ObjectStore.get/head/putPrimary`（孤儿 data → 抛 `StorageException` / 拒绝覆盖写「需人工恢复」）
删除进行到 meta 已删、data 未删时掉电；重启后 `sweepTempFiles` 只清 `.tmp`，孤儿 `object.data` 永久残留；此后该 key GET/HEAD 恒 500、PUT 恒被拒（防 version 重置），**必须人工上机删文件**。
**修复**：meta 不存在且无 `.corrupt` 残留时，孤儿 data 可判定为删除中间态直接清理。

### P2-4　VERIFYING 仅比对对象计数，无内容摘要比对
**位置**：`MigrationEngine.runTask`（VERIFYING：`targetCount < sourceCount` 即失败）；`StorageCapability.partitionCount`/`verifyCount`
等量替换（删 1 增 1）、字节级损坏、P0-1 的窗口错位都表现为「计数达标」；反之迁移期间源端有删除则计数抖动 → 误报 FAILED 重试。已有逐片 SHA-256 兜传输层，但缺「分区级 digest 对账」。
**修复**：cutover 前做分区级 digest 对账。

### P2-5　`minMoveRatio` 门控吞掉小规模扩容的重平衡，新节点长期空载
**位置**：`runtime/placement/.../RebalancePlanner.shouldRebalance:63-73`（移动比例 < minMoveRatio 直接 false）；`ReconcileLoop.healOrRebalance:886-890`；`SchedulerConfig`（默认 0.10）
N≥10 集群加 1 节点，HRW 目标环移动比例 ≈ 1/(N+1) < 10% → 重平衡**永不触发**且无「逐步追平」机制；新节点分不到主分区，扩容只加心跳不加容量，负载倾斜持续，直到攒够节点一次性越过阈值（届时又是移动风暴）。
**修复**：增加「低水位慢速均衡」通道（低于阈值时按每周期限量搬迁）。

### P2-6　负载指标采集与均衡决策完全脱节（无负载感知闭环）
**位置**：采集侧 `runtime/cluster/.../OsResourceMonitor.java` + `ResourceSnapshot`（CPU/内存/磁盘随心跳 gossip）；决策侧 `ReconcileLoop.reconcile:552-556`（权重只取 `NodeInfo.weight()`——注册时静态配置，全生命周期不变）；全代码无依据资源快照调整权重或触发搬迁的路径，**无运行时改权重的管理端点**
某节点磁盘 90%、CPU 打满，另一节点空载——只要都 ACTIVE，放置环纹丝不动；LB 层同样只有静态权重，不消费实时负载。所谓「负载均衡」实际是**静态加权分区计数均衡**。磁盘写满不会让节点被摘除，只在写路径报错。
**修复**：权重管理端点 + 可选磁盘水位降权 + 负载反馈环。

### P2-7　退役 DEAD 节点与 DEGRADED 隔离互相锁死：DRAINING 永久卡住
**位置**：`runtime/server/.../decommission/RuntimeDecommissionCoordinator:152-168`（`hasPrimary → return` 无限等待）；隔离语义在 `ReconcileLoop.healOrRebalance`（DEGRADED 分区放置仍指向死亡属主）；`DecommissionRecord.force` 字段只透传不消费（`:246`）
节点 X 死亡 → 无副本分区被隔离（放置仍指 X）→ 运维对 X 发起退役（含 force=true）→ `advanceDraining` 每轮看到 PRIMARY 残留直接 return → 退役永久停在 DRAINING，除非先对每个隔离分区逐一 `force-adopt`。force 语义没有贯通到隔离门控。
**修复**：force=true 时 DRAINING 门控放行隔离分区（联动 force-adopt）。

### P2-8　LB 入口节点：人工指定 SPOF + 阻塞式反代线程模型可「假活」
**位置**：`runtime/server/.../lb/LbProxyFilter.java`（每请求占一个 Tomcat 线程同步转发）；`runtime/lb/.../LbConfig.java`（`requestTimeoutMs` 默认 3600000=1h）；`负载均衡方案.md §8`（自认 SPOF 与线程容量为既定取舍）
入口宕机 → 全部外部流量中断，需人工改指（无自动接管/VIP）；大文件并发经入口，每请求一线程最长挂 1h，Tomcat 线程池耗尽后入口「假活」（注册表仍 ACTIVE，被动健康探测发现不了）。
**修复**：入口自动接管/VIP；主动健康探测；流式转发降低线程占用。

### P2-9　CACHE 默认 rf=1 + 隔离策略：缓存节点死亡 → 分区 503 而非降级
**位置**：`SchedulerConfig.rfFor`（CACHE 专属 rf 默认 1，注释：rf>1 会产生「幽灵副本」因 cache 无复制器）；`CacheGateway.checkNotDegraded`（DEGRADED → 503）；`ReconcileLoop` 治愈宽限期 30s 后隔离
任一 CACHE 节点死亡超 30s 宽限期，其承载全部分区对客户端 503 硬失败，直到节点重启或人工 force-adopt。对「缓存」这一本可 miss 回源的场景，把节点故障放大为**主动拒绝服务**；rf>1 又不可用（无 cache 复制器），可用性无横向手段。
**修复**：提供「隔离期降级为空读/直写新主」开关。

### P2-10　死源 = 空分区迁移的「数据丢失窗口」依赖 quarantine 开关兜底
**位置**：`RoutingPartitionAdapter.remoteOrNull`（源不可解析 → WARN + 空迭代器，日志自认 "data loss window if source"）；`ReconcileLoop.healOrRebalance`（`healingQuarantineEnabled` 默认 true 走 DEGRADED 隔离，**false 时退回空分区迁移 + cutover 覆盖放置**）
默认配置下隔离门是好的；但开关一旦关闭，节点永久失联超宽限期（默认仅 30s）即「以空迁有」，属主改挂他节点，原盘数据虽在却再无路由指向。30s 宽限期对「押注重启」偏短。
**修复**：宽限期取值上调；配置退化路径加显式告警/二次确认。

### P2-11　成员视图缺乏跨节点因果序，只有 per-node `state_epoch`
**位置**：`MembershipService.merge()/accept():655-751`（合并规则「epoch 高者胜；同 epoch 悲观状态胜 DEAD>SUSPECTED>ACTIVE」）
`state_epoch` 是每节点独立计数，无法表达跨节点因果（无 vector clock/全局版本）。多观察者并发写同一节点状态到 DB 时，最终态取决于 DB 行锁顺序。缓解：`directFromSource`（自报）恒被采纳规避 stuck-DEAD；S12 纪元防护丢弃陈旧他报回写。收敛性尚可，稳态有短暂抖动（最终一致 gossip 固有代价）。

### P2-12　`replaceAll` 混用 app 墙钟与 DB 时钟计算 `valid_after`
**位置**：`JdbcPlacementStore.replaceAll:187-192`（`long now = System.currentTimeMillis()` 与 `maxLeaseUntil`(DB钟) 取 `Math.max`）；`cutover:303`（`updated_at` 用 app 钟，`valid_after` 用 DB `NOW()`）
`valid_after = max(app_now, db_maxLeaseUntil) + margin` 跨时钟求最大，主机与 DB 时钟偏移会平移新属主可写时刻。仅出现在 bootstrap（空表）和 drain-to-empty 路径，影响面小于 P0-2。

### P2-13　单向 ack 丢失造成非对称存活判定，放大 P1-8 误杀
**位置**：`MembershipService.heartbeat:305-314`（服务端对请求方 `recordSignal`）与 `sendHeartbeat:464-480`（仅客户端收到 ack 才 `recordSignal`）
若网络只丢 B→A 方向的 ack：A 收不到 ack 判 B 死；B 收到 A 的请求判 A 活。非对称视图 + 默认单观察者直写 DEAD = A 把健康的 B 全局判死。属心跳协议固有特性，与 P1-8 叠加后危害放大，建议随 P1-8 一并开启仲裁。

## 5. 做得好的地方（简要）

1. **崩溃一致性写路径扎实**：`ObjectStore.writeObject` 的 tmp→fsync(data)→fsync(meta)→rename 两段提交（T5 旧 data 备份可回滚，消除「新数据+旧 meta」错配对）、rename 后目录 fsync、meta 可见即数据完整；C4 之后 fsync 真实生效。
2. **数据面 fencing 三重且以 DB 时钟为准**：放置 epoch CAS（`cutover/promoteReplica` 的 `WHERE epoch=?`）+ `valid_after_ms`（新主等旧租约过期 + 1s）+ 本地租约 fail-closed；`MigrationEngine` 切主走 `expectedEpoch` CAS，失配抛 `FencedException`；`replaceAll` 前 `FOR UPDATE` 读旧租约上界防竞态。这是防僵尸属主双写的核心，设计正确（唯一软肋见 P0-2 的本地时钟锚定）。
3. **P0-2 DEGRADED 隔离门**（默认开启）：属主死且无副本时拒绝流量、放置留盘押注重启，而非以空分区覆盖放置表——避免了大多数自愈系统最常见的「治愈即永久丢数据」错误，属主回归自动解除。
4. **决策仲裁清晰，无多主决策冲突**：所有放置/均衡/治愈/排空决策收敛到 DB 租约选出的单一 leader（DB 时钟消除节点间时钟偏移 S14）；执行层多节点并发安全——状态机 CAS 跃迁、`TaskContendedException` 与业务失败严格区分、启动 `resumeAll` 复核最新状态防非法跃迁。
5. **防振荡/防惊群成体系**：重平衡 = 移动比例门控 + 冷却 + 失败也占冷却预算（防任务表爆炸）；命令/迁移分批（256）+ 批间续约（防长操作失租走马灯）；治愈宽限期押注重启（防 GC 停顿触发不可逆迁移）；HRW 最小移动 + 结果确定性（跨节点可复现）。
6. **缩容排空总体安全**：freeze 停新写 → 副本提升优先（无损免迁移）→ 迁移（断点续跑 + 每片 SHA-256 端到端校验 + SYNCING 追增量至静默）→ verifyCount 对账 → 才 stop；`DesiredStateWriter` 有「排空最后节点」保护；放置表残留 PRIMARY 即拒绝进入 REMOVING。
7. **路由层重试语义克制**：网关只对 fencing 拒绝（写未生效）刷新重试一次；`StorageGateway` 明确区分「本地路径可重试（读流未消费）/远端转发不重试（流已消费会截断对象）」；LB 写方法绝不重试、GET/HEAD 仅连接类失败重试一次并有 `X-RT-LB-Forwarded` 防环——都避免了重复写/写放大。
8. **Phi-Accrual 故障检测实现扎实**：正态近似 + `minStdDeviation` 下限防零方差过敏 + `acceptablePause` 容忍 GC + 暖窗期回退固定超时 + `deadConfirmations` 连续超阈防抖。
9. **IngestObserver 生命周期防护（T2）**：responded CAS 唯一应答、aborted 位 + 限时入队防 gRPC 回调线程钉死、毒化哨兵、丢弃/判死计数可观测。
10. **端到端校验与幂等**：迁移逐片 SHA-256（引擎只算一次、传输层复用）、接收端校验不符要求重发（有限次 + 退避）；`putReplica` version 防回退幂等 + T26 同版本异 etag 冲突检测计数；复制后远端 HEAD 复核 version+etag 不匹配重传一次（T6）。
11. **启动/停机编排严谨**：启动 DDL bootstrap → gRPC 服务注册（严格早于 host.start）→ membership.start → nodeRuntime.start（register JOINING → 绑端口 → 自检 → ACTIVE → 心跳）→ 能力注册 → 收敛等待（≤3s 避免首查基于残缺视图误判 DEAD）→ 确定性首查 → resumeAll；任一步失败 fail-fast 且内联 tombstone 回滚不留 JOINING 孤儿。停机倒序幂等，membership.stop 主动 recall 全部怀疑票避免离群后旧票凑齐法定人数误杀。
12. **channel 重建规避 JVM DNS 负缓存**：连续 3 次发送失败重建 channel，`channels.compute` 原子重建避免并发泄漏——很实战的防御。
13. **文档-代码纪律好**：几乎所有历史缺陷修复处都有编号注释（S3/S5/T19/T20/C17/P0-2…）锚定审查条目，测试树含大量 BugRepro 回归测试。

## 7. 核心结论

这是一套完成度和自我修复意识都相当高的「中心决策 + DB 真源 + 去中心执行」架构，多数经典分布式陷阱（双主决策、振荡、惊群、缩容丢数据、路由重试放大、治愈即丢数据）已有针对性机制，单机写路径与 fencing/租约层质量很高。

**2026-10-20 分析时点最主要的真实风险（P0/P1 批次已修复）**：
1. ~~迁移/重平衡 cutover 的写丢失窗口（P0-1）~~ → ✅ 已修复：源分区迁移期冻结 + 键型游标 + 断点从零重放 + 落盘后二次 fencing；
2. ~~本地写租约的时钟锚定（P0-2）~~ → ✅ 已修复：单调钟 + DB 时钟锚点；
3. ~~副本与迁移异步链路的版本/顺序缺口（P1-3~P1-7）~~ → ✅ 主体修复：删除版本护栏、backlog 重读、对账比 etag、反熵 prune、半同步默认开、排空屏障；**残项**：内存态 backlog、非全局 version、死主 failover 窗口（文档化权衡）。

**仍开放的架构级缺口**：
- 控制面单库（P1-1）——控制面可用性 == DB 可用性，需运维 HA 方案；
- φ 故障检测墙钟（P2-1 残余）——需单调钟改造；
- 节点间 gRPC 无认证（P2-2）——需 mTLS；
- 负载感知闭环缺失（P2-5/P2-6）——静态加权均衡；
- 复制意图不持久（backlog 内存态）与 version 非全局唯一——全局版本方案（`epoch<<32|seq`）为中期项。
