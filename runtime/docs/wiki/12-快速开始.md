# 12. 构建与运行指南

> 覆盖：环境前置、本地构建（后端 + 前端）、单节点运行、Docker 多节点集群、动态扩容、HTTP 端点操作、测试执行与常见问题。

## 1. 环境前置

| 项 | 要求 | 说明 |
|---|---|---|
| JDK | 21+（`maven.compiler.release=21`） | |
| Maven | 3.9.x | 仓库自带 wrapper（`mvnw` / `mvnw.cmd`），无需本机安装 |
| PostgreSQL | 任意（测试容器用 16；docker-compose 部署默认宿主机 PG 18:5432/ww） | 仅 `runtime.store=jdbc` 模式需要；memory 模式零外部依赖 |
| Node.js + pnpm | 可选 | 仅构建 runtime-ui 管理前端需要（pnpm 9） |
| Docker | 可选 | Testcontainers 冒烟 IT 与 deploy-runtime.sh 集群部署 |

## 2. 构建

```powershell
# 全量构建（含单测）
.\mvnw.cmd -f runtime install

# 快速构建可执行 jar（跳过测试；改过兄弟模块源码后必须先刷新本地快照）
.\mvnw.cmd -f runtime -DskipTests install

# 只构建 server 及其依赖链（-am 连带构建依赖，规避 ~/.m2 旧快照陷阱）
.\mvnw.cmd -f runtime -pl server -am -DskipTests package
```

```bash
# 管理前端（Vue 3 + Vite，产物注入 server 静态资源后再打 jar）
cd runtime/runtime-ui && pnpm install && pnpm build
# 输出拷贝到 runtime/server/src/main/resources/static/（deploy-runtime.sh 自动串联）
```

产物：`runtime\server\target\runtime-server-1.0-SNAPSHOT.jar`（Spring Boot repackage 的可执行 fat jar，主类 `com.ww.runtime.server.RuntimeServerApplication`，内置管理台 UI）。

> **单模块构建陷阱**：`-f runtime/server` 单模块构建从 `~/.m2` 解析兄弟模块快照；改了兄弟模块源码而未 `install` 时会用到旧 jar（实测踩到：旧 CapabilitySchema 建不出表）。规范：改兄弟模块后先 `mvnw -f runtime install`，或始终用 `-pl server -am`。

## 3. 单节点运行

### 3.1 memory 模式（零外部依赖，最快上手）

全部仓库为进程内实现：不建 DataSource、不执行 DDL、不触碰数据库、日志不落库（仅广播）。

```powershell
$env:RUNTIME_STORE='memory'          # 进程内存储
$env:RUNTIME_NODE_ID='node-1'
$env:RUNTIME_NODE_GRPC_PORT='0'      # 0 = 随机端口
$env:SERVER_PORT='0'                 # 随机 HTTP 端口（固定端口可指定如 8091）
java -jar runtime\server\target\runtime-server-1.0-SNAPSHOT.jar
```

启动即完成：gRPC 绑定 → 注册 ACTIVE → 采样/心跳线程 → leader 租约 → ReconcileLoop 首轮收敛 → MOCK 能力拉起（`mock-desired` 默认 true）。加 `$env:RUNTIME_CAPABILITIES_CACHE_DESIRED='true'` / `STORAGE_DESIRED=true` 可同时拉起数据面能力。

### 3.2 jdbc 模式（真实 PostgreSQL）

先准备数据库（任一 PG 实例，建库与用户）：

```powershell
# 例：Docker 起一个临时 PG
docker run -d --name rt-pg -e POSTGRES_DB=rt -e POSTGRES_USER=rt -e POSTGRES_PASSWORD=rt `
       -p 55432:5432 postgres:16
```

再启动节点（环境变量覆盖 `application.yml`）：

```powershell
$env:RUNTIME_NODE_ID='node-1';      $env:SERVER_PORT='8091'
$env:RUNTIME_NODE_GRPC_PORT='9101'; $env:RUNTIME_NODE_HOST='127.0.0.1'
$env:SPRING_DATASOURCE_URL='jdbc:postgresql://127.0.0.1:55432/rt'
$env:SPRING_DATASOURCE_USERNAME='rt'; $env:SPRING_DATASOURCE_PASSWORD='rt'
$env:RUNTIME_STORE='jdbc';          $env:RUNTIME_CAPABILITIES_MOCK_DESIRED='true'
java -jar runtime\server\target\runtime-server-1.0-SNAPSHOT.jar
```

启动自检（Fail-Fast）：PG `SELECT 1` 可达 → 6 个 Schema bootstrap 建齐 8 张表（`rt_node`/`rt_cluster_config`/`rt_decommission`/`rt_capability_state`/`rt_partition_placement`/`rt_scheduler_lease`/`rt_migration_task`/`rt_log`，幂等）→ 注册/心跳/租约/ReconcileLoop/日志批量线程就绪。任一步失败即终止启动。

## 4. 多节点组集群

### 4.1 手工多进程（同一 PG）

各节点指向**同一个 PG**，用不同的 `RUNTIME_NODE_ID` / 端口即可自动组集群（无固定 Master，leader 由租约竞选产生）：

```powershell
# node-2（另开一个终端）
$env:RUNTIME_NODE_ID='node-2';      $env:SERVER_PORT='8092'
$env:RUNTIME_NODE_GRPC_PORT='9102'; $env:RUNTIME_NODE_HOST='127.0.0.1'
$env:SPRING_DATASOURCE_URL='jdbc:postgresql://127.0.0.1:55432/rt'
$env:SPRING_DATASOURCE_USERNAME='rt'; $env:SPRING_DATASOURCE_PASSWORD='rt'
java -jar runtime\server\target\runtime-server-1.0-SNAPSHOT.jar

# node-3 同理：SERVER_PORT=8093 / RUNTIME_NODE_GRPC_PORT=9103 / RUNTIME_NODE_ID=node-3
```

集群行为：

- 节点经 gRPC 心跳互发现（gossip 视图合并 + 版本化增量 ack），注册表互通；
- 任一节点抢到 `rt_scheduler_lease` 租约成为 leader，执行 Desired→Actual 收敛；
- 新节点加入（写 desired=ACTIVE）后 leader 重算放置环，按最小移动原则迁出分区；
- 关停 leader 后其余节点 ≤2×TTL 接管租约。

> 提示：地址一律用 `127.0.0.1` 而非 `localhost`（后者可能解析为 `::1`，而监听是 IPv4-only）。

### 4.2 Docker 四节点集群（推荐测试拓扑）

`runtime/docker-compose.yml` + `runtime/Dockerfile` + `runtime/deploy-runtime.sh` 提供一键部署：

```bash
./runtime/deploy-runtime.sh all     # 编译 jar + 构建前端 + 构建镜像 + 启动 4 节点
./runtime/deploy-runtime.sh verify  # 校验前端静态产物
```

要点（与 compose 注释一致）：

- 数据库复用宿主机 PostgreSQL（容器经 `host.docker.internal` 访问；需 PG `listen_addresses` 含 docker 网桥段且 pg_hba 放行）；
- 加速时序参数：心跳 500ms / suspect 2 / dead 4 / TTL 5s / 调谐 500ms / 冷却 3s——仅测试用，生产走默认值；
- `RUNTIME_REPLICATION_FACTOR=2`（STORAGE 双副本，故障可无损提升）、`RUNTIME_HEALING_GRACE_PERIOD_MS=30000`；
- **P1-9 多机部署建议**：每个物理机架/可用区配置 `RUNTIME_NODE_ZONE=<rack-id>`，副本自动跨域摆放；单机 compose 可不配置（行为不变）；
- 2026-10-20 起默认：STORAGE 半同步复制开启（`RUNTIME_CAPABILITIES_STORAGE_SEMI_SYNC_ENABLED=false` 回退异步）、多数仲裁判死开启（`RUNTIME_SUSPICION_QUORUM_ENABLED=false` 回退单观察者直写）；
- CACHE/STORAGE 全开启，每节点独立数据卷（对象数据/AOF 不可跨节点共享）；
- `restart: "no"`：kill 后保持停止，便于故障注入（DEAD 检测/租约接管）；
- JVM 堆钉 4g + OOM heapdump（迁移并发下防默认人体工学堆不足）。

## 5. 动态扩容

```bash
./runtime/scale-out.sh 5        # 向已有集群添加 node-5（HTTP 8095，gRPC 9100 compose 内部）
./runtime/scale-out.sh --mock 6 # 同时启用 MOCK
```

新节点 CACHE/STORAGE 默认禁用，需在管理页面（或 `PUT /rt/nodes/node-5/capabilities/CACHE/desired`）启用；leader 下个调谐周期自动重算环并重平衡。

## 6. HTTP 端点操作速览

任选一个节点的 REST 端口操作（管理面只写期望态，完整表见 [10-服务端模块.md](10-服务端模块.md) §7）：

```powershell
# 集群状态快照 / SSE 实时流
curl http://127.0.0.1:8091/rt/status
curl http://127.0.0.1:8091/rt/status/stream

# 扩容：让 node-3 承接 MOCK（调度器自动拉起 + 重平衡）
curl -X PUT http://127.0.0.1:8091/rt/nodes/node-3/capabilities/MOCK/desired `
     -H "Content-Type: application/json" -d '{"desired":"ACTIVE"}'

# 排空：node-1 下线（freeze→迁移/提升→cutover→actual=DISABLED）
curl -X PUT http://127.0.0.1:8091/rt/nodes/node-1/capabilities/MOCK/desired `
     -H "Content-Type: application/json" -d '{"desired":"DISABLED"}'

# 退役（先预检，最后主持有者需 force）
curl -X POST http://127.0.0.1:8091/rt/nodes/node-4/decommission/precheck
curl -X POST http://127.0.0.1:8091/rt/nodes/node-4/decommission -H "Content-Type: application/json" -d '{\"force\":true}'

# 数据面：CACHE / S3 网关（任意节点进，按 placement 路由）
curl -X PUT "http://127.0.0.1:8091/cache/k1?type=text" -d "v1"
curl http://127.0.0.1:8091/storage/b1/a/b.txt --output out.txt

# 迁移任务观测与操作
curl "http://127.0.0.1:8091/rt/migration/tasks?scope=active"
curl -X POST http://127.0.0.1:8091/rt/migration/resume

# 日志：历史查询 + 实时流
curl "http://127.0.0.1:8091/rt/logs?level=ERROR&size=20"
```

管理台 UI：浏览器打开 `http://127.0.0.1:8091/`（集群/缓存/存储/日志四个页面）。

## 7. 测试

```powershell
# 全部单测（84 个测试类；Surefire 只跑 *Test）
.\mvnw.cmd -f runtime test

# Testcontainers PG 冒烟 IT（Failsafe 在 integration-test/verify 阶段跑 *IT）
.\mvnw.cmd -f runtime/server clean verify
```

| 套件 | 说明 |
|---|---|
| 单测 84 类 | 状态机合法/非法跃迁矩阵、租约互斥与接管、HRW 最小移动与数学基线、并发 cutover、迁移断点续跑零差对账、跨节点路由（Routing 三节点端到端）、CACHE/STORAGE 引擎（Stream 消费组/AOF 重写/网关合并/复制对账）、ReconcileLoop 六阶段与四个 bug 复现固化等 |
| `RuntimePostgresSmokeIT` | 真实 PG 容器：各 Jdbc* store + Schema bootstrap 冒烟 |
| `RuntimeLogSmokeIT` | 真实 PG 容器：LogSchema 幂等 + 批量写 + 分页过滤 |
| `RuntimeServerIntegrationTest` | `store=memory` 全装配集成测试，无需 PG |

## 8. 常见问题

| 现象 | 原因与处理 |
|---|---|
| 启动失败：PostgreSQL self-check failed | PG 不可达或凭据错误；检查 `SPRING_DATASOURCE_*` 与 PG 是否监听 IPv4（用 `127.0.0.1` 而非 `localhost`） |
| 建表失败 / 行为与源码不符 | 单模块构建用到了 `~/.m2` 旧兄弟模块快照；重跑 `.\mvnw.cmd -f runtime install` 或用 `-pl server -am` |
| gRPC 端口冲突 | `RUNTIME_NODE_GRPC_PORT=0` 用随机端口（单测做法），或给每个节点分配独立端口 |
| 多节点互相看不见 | 各节点未指向同一 PG，或 `RUNTIME_NODE_HOST` 配成了对端不可达的地址 |
| 容器重启后 gRPC "Unable to resolve host" | JVM DNS 负缓存；镜像已内置 `-Dsun.net.inetaddr.negative.ttl=0`；membership 侧另有连续失败重建通道兜底 |
| 迁移高峰节点 OOM | 钉 JVM 堆（见 Dockerfile JAVA_OPTS）并调低 `RUNTIME_MIGRATION_MAX_CONCURRENT` |
| HTTP/2 流式传输异常（HPACK/巨型消息） | Netty 版本被抬高破坏钉版；确认 runtime-parent 的 netty-bom 4.1.100.Final 生效 |
| kill 节点后很久才接管/重算 | 生产默认时序较保守（TTL 10s、suspect 3、dead 6、治愈宽限 30s）；可按需调小 `RUNTIME_SCHEDULER_TTL_MS` 等 |
| 大集群故障分区迟迟不治愈 | 确认走的是治愈分支（from∉alive 免比例/冷却门控）；无副本时先等 `healing-grace-period-ms` 押注重入 |
