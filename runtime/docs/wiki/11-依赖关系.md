# 11. 依赖关系 — 模块依赖图与分层铁律

> 本文覆盖：runtime 家族 11 个 Maven 模块的依赖图、分层铁律与依赖门禁、第三方依赖管控、ww 仓库既有系统（common/admin）的合并移除记录、以及模块间的**代码级耦合点**（端口与适配）。

要点：

- **common 与 proto 是零模块依赖的基石**（proto 仅依赖 grpc/protobuf 第三方库）。
- **capability 与 placement 互不依赖**——二者在 scheduler/migration/data 处汇合；capability 需要的放置视图经 `PlacementView` 端口由 server 适配（见 §4）。
- **scheduler 与 migration 互不依赖**——scheduler 经 `MigrationCoordinator` 端口调用迁移，由 server 适配。
- **membership 不依赖 cluster**（心跳所需的节点目录/状态回写均为自身端口 `PeerDirectory`/`StateSink`，由 server 装配时用 NodeRegistry 实现）。
- **migration 不依赖 data，data 依赖 migration**（单向）：data 的 Cache/StoragePartitionAdapter 实现 migration 的 `PartitionDataAdapter` SPI；跨节点路由的 `RoutingPartitionAdapter` 在 **migration 模块内**（能力无关）。
- **runtime-log 是最薄的独立模块**（仅依赖 common + logback/slf4j）：采集缓冲与总线，落库/暴露由 server 装配。
- **runtime-data 是数据面能力实现层**（CACHE/STORAGE CapabilityModule + 引擎 + 网关/复制器/gRPC 数据面）：依赖 capability（SPI）+ placement（Partitioner）+ migration（PartitionDataAdapter）+ proto（storage.proto/cache.proto 契约）。**common/storage 与 common/cache 模块均已删除**：storage 引擎类（ObjectStore/DriveManager/SetLocator/BucketStore 等 16 个）迁入 `storage/engine` 包，cache 引擎类（SimpleCache/StreamStore/AofService/Codec 等 20 个）迁入 `cache/engine` 包，模块自身保持零 Spring（enforcer 门禁）。

## 2. 分层铁律与依赖门禁

架构分层铁律（本文与 [01-架构总览.md](01-架构总览.md) §5 定义）：

```
server → {各核心模块} → {proto, common}；任何模块不得反向依赖 server
```

具体约束（分层）：

| 层 | 模块 | 约束 |
|---|---|---|
| 组装层 | server | 唯一允许 Spring；聚合一切；无人依赖它 |
| 编排层 | scheduler、migration | 可依赖下述所有层 |
| 数据面能力层 | data、log | CACHE/STORAGE 实现与日志采集总线；零 Spring（enforcer 门禁）；可依赖领域层与基建层 |
| 领域层 | cluster、membership、capability、placement | 彼此几乎正交（仅 cluster 依赖 proto/common 基建） |
| 基建层 | proto、common | 零模块依赖；不依赖任何上层 |

补充门禁：

- 核心模块（server 以外）**零 Spring 依赖**——保证未来可脱离 Spring 独立运行（蓝图 §6）。
- 控制面元数据只走 PostgreSQL；数据面大数据只走 gRPC Stream——**禁止**把数据库当大数据搬运通道。
- 管理面 API 只写 Desired State，禁止直接 UPDATE actual。

## 4. 模块间代码级耦合点（端口与适配）

Maven 依赖之外，模块协作的**全部接缝**收敛为少量接口（端口），实现由 server 装配时适配——这是「模块可独立演进」的关键：

| 接缝 | 端口（接口） | 提供方 | 消费方 | server 侧适配 |
|---|---|---|---|---|
| 放置视图 | `capability.PlacementView`（`owner()` 主 / `holders()` 主+副本） | placement（数据在 `PlacementStore`） | capability（fencing 校验）、data（网关路由/Replicator 选副本） | `PlacementViewAdapter` |
| 迁移协调 | `scheduler.MigrationCoordinator` | migration（`MigrationEngine`） | scheduler（drain/重平衡时迁移） | `RuntimeMigrationCoordinator` |
| 退役驱动 | `scheduler.DecommissionDriver`（`advance()`） | cluster（`DecommissionStore` 记录） | scheduler（Leader 每周期推进） | `RuntimeDecommissionCoordinator` |
| 节点命令 | `scheduler.NodeCommandChannel` | gRPC 远程 + 本地回退 | scheduler（下发启停/冻结） | `GrpcNodeCommandChannel`（self 走 `LocalNodeCommandChannel`） |
| 成员目录 | `membership.PeerDirectory` / `StateSink` | cluster（`NodeRegistry`） | membership（gossip 心跳/故障回写） | `RuntimeAssembly` 装配时 lambda/匿名适配 |
| 能力节点目录 | `data.CachePeerDirectory` / `StoragePeerDirectory`（含 `servingPeers()`） | cluster（`NodeRegistry` + `CapabilityStateStore`） | data（网关转发/副本复制/fan-out 选点） | `RuntimeAssembly` 装配时适配 |
| gRPC 宿主 | `proto.GrpcServerHost` | proto | membership/migration/cluster-control/health/storage/cache/log 各 Server | `RuntimeBootstrapper` 统一注册顺序 |
| 迁移数据面 | `migration.PartitionDataAdapter` | migration（Mock）+ data（`CompositePartitionAdapter`：MOCK+CACHE+STORAGE） | migration（`MigrationEngine` 经 `RoutingPartitionAdapter` 跨节点路由；`MigrationServer` 走本地组合） | `RuntimeAssembly` 接线 |
| 期望态写入 | `scheduler.DesiredStateWriter` | scheduler | server Admin API / Bootstrapper / 退役流程 | 直接 Bean |
| 日志链路 | `runtime-log` 的 `LogBuffer`/`LogBus`（进程内静态/Bean） | runtime-log（logback 挂点） | server（批量落库/SSE/gRPC 聚合） | `RuntimeAssembly.logBus()` + `RuntimeLogBatchWriter` |

## 5. 与 ww 仓库既有系统的关系

根 pom `ww` 现仅聚合 `runtime`（本 Wiki 主体）；原既有系统（`common`、`admin`）已全部合并移除。

- **common/storage 已删除合并**：原 `common/storage` 的引擎类（ObjectStore/DriveManager/SetLocator/BucketStore/ObjectMetadataCache/CryptoCodec 等 16 个）迁入 `runtime-data` 的 `storage/engine` 包（改包名、去 Spring 注解）；其自管分布式层（HRW NodeRouter/并行复制/FailoverManager/MigrationService/InternalNodeClient 等 11 类）**整体废弃**，由 runtime 框架的 placement/scheduler/migration/StorageReplicator 统一接管。
- **common/cache 已删除合并**：原 `common/cache` 的纯引擎类（SimpleCache/StreamStore/AofService/Codec 等 20 个）迁入 `runtime-data` 的 `cache/engine` 包（改包名、去 Spring 注解）；其自管集群层（TCP CacheProtocol/CacheServer/ClusterMembership/FailoverManager/RebalanceManager/DistributedCache/cluster-rpc 桥接等 12 类）**整体废弃**，由 runtime 框架的 membership/placement/scheduler/migration 统一接管；网关路由由 `CacheGateway` + `cache.proto`（ForwardPut/PutIfAbsent/Get/Delete）实现（对齐 StorageGateway 模式）。
- **common/admin 整体下线**：admin 模块（Shiro 会话/授权缓存、`/cache/**` 与 `/cache/admin/**` REST、stream HTTP 调试接口、HRW 集群管理）全部移除；CACHE 数据面唯一入口为 runtime-server `/cache`（网关自动转发），STORAGE 为 `/storage`（见 [10-服务端模块.md](10-服务端模块.md) §7）。`common/cluster-rpc`、`common/common-cluster`、`common/common-database` 随之删除。
- **runtime-log 承接原 admin 的日志采集链**：logback → DbLogAppender → LogBuffer → 批量落库 `rt_log` + SSE 实时流 + 跨节点 gRPC 聚合（原 admin 的 SysLog/InternalLogController 体系不复存在）。
- **runtime-data 对 ww 仓库外部零模块依赖**：CACHE 与 STORAGE 引擎均已完全内化于 runtime-data。
- **共享的只有构建基线**：根 pom 的 Boot 4.0.7 parent、JDK 21、grpc/protobuf 版本与编码约定。

## 6. 循环依赖的规避设计

三个潜在的循环依赖点及其解法：

1. **capability ⇄ placement**（能力需要知道分区归谁 / 放置需要知道能力拓扑）：
   capability 定义 `PlacementView` 端口只返回 `Owner(node, epoch)`，不依赖 placement 的任何类；server 用 `PlacementViewAdapter` 桥接。
2. **scheduler ⇄ migration**（调度要触发迁移 / 迁移完成要更新放置）：
   scheduler 定义 `MigrationCoordinator` 端口；migration 只依赖 placement（`cutover` 切主），不依赖 scheduler。
3. **membership ⇄ cluster**（心跳需要节点目录 / 注册表需要心跳判活）：
   membership 自持 `PeerDirectory`/`StateSink` 端口与故障检测状态机，cluster 的 `NodeRegistry` 仅是目录实现之一（server 装配时注入）。

## 7. 版本与构建坐标

| 模块 | groupId:artifactId | version |
|---|---|---|
| 聚合 | `com.ww:runtime-parent`（packaging=pom） | 1.0-SNAPSHOT |
| 各子模块 | `com.ww:runtime-{common,proto,cluster,membership,capability,placement,scheduler,migration,log,data,server}` | 1.0-SNAPSHOT |

- 构建顺序由 Maven Reactor 从依赖图推导：common/proto → cluster/membership/capability/placement → scheduler/migration/log → data → server。
- `runtime-ui`（Vue 3 + Vite + pnpm 前端工程）**不在 Maven Reactor 内**：`pnpm build` 产物拷贝进 `runtime/server/src/main/resources/static`，随 fat jar 发布（deploy-runtime.sh 负责串联）。
- **单模块构建陷阱**（实测）：`-f runtime/server` 单模块构建从 `~/.m2` 解析兄弟模块快照；改了兄弟模块源码而未 `install` 时会用到旧 jar。规范：改兄弟模块后先 `mvnw -f runtime install`，或始终用 `-pl server -am`（连带构建依赖）。详见 [12-快速开始.md](12-快速开始.md) §2。
