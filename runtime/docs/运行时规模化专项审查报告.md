## 1. 缓存模块（44 项）

### 1.1 P0 致命

#### 缓存-1：AOF 重写把 ZSet 误当 Hash 写入，重启回放必崩，节点无法启动

**位置**：`AofService.java:814-826`（writeHashEntries）+ `SimpleCache.java:1246-1255`（getAllHashEntries）

```java
// SimpleCache.getAllHashEntries —— 未排除 ConcurrentSkipListMap（ZSet 的实现类）
public List<Map.Entry<K, Map<String, V>>> getAllHashEntries() {
    ...
    if (val instanceof Map) {        // ← ZSet 也是 Map，被纳入
        result.add(...);
    }
}
// 对比：同文件 getAllKeyValueEntries（1234 行）正确地排除了
//   !(val instanceof ConcurrentSkipListMap)
// AofService.writeHashEntries：
byte[] cmd = encodeCommand(OP_HSET, key, fe.getKey(), fe.getValue()); // fe.getKey() 实为 Double(score)
// 回放 OP_HSET: cache.hset(key, (String) args[0], args[1]) → ClassCastException
```

- **触发场景（海量数据）**：只要缓存中存在任意一个 ZSet 且触发 AOF 自动重写（默认开启，64MB/100% 增长触发），重写后的 AOF 即含毒记录；下次重启回放时抛 CCE。
- **根因**：`replay()` 只 catch `IOException`，CCE 是 RuntimeException 直接穿透 → `CacheCapability.start()` 失败。`CacheCapability.exportPartition` 中明确注释"SkipListMap 也是 Map——它属 ZSET，此处跳过"，证明作者知道此陷阱但 AOF 重写路径漏了同样的防护。
- **修复**：`getAllHashEntries()` 增加 `&& !(val instanceof ConcurrentSkipListMap)` 排除；回放循环对单条记录增加 `catch (RuntimeException)` 容错，避免单条毒记录拖死整个启动。

#### 缓存-2：事务（MULTI/EXEC）内写操作的 AOF 记录格式损坏：回放启动失败或数据静默污染

**位置**：`SimpleCache.java:243-244`（queueOrExec 入队时 `joinArgs` 拼成 tab 字符串）→ `SimpleCache.java:850-852`（exec 调 `aofService.log(cmd.aofOp, cmd.aofKey, cmd.aofArgs)`）→ `AofService.java:222-230`（整串当单个 arg 编码）

```java
// exec 内：aofArgs 是 joinArgs 产物 "value\t1000"（单字符串）
aofService.log(cmd.aofOp, cmd.aofKey, cmd.aofArgs);
// 回放 OP_PUT: cache.put(key, args[0]) → 值变成 "value\t1000"，TTL 丢失
// 回放 OP_HSET: cache.hset(key, (String) args[0], args[1]) → args 只有 1 个 → ArrayIndexOutOfBounds
```

- **触发场景（高并发）**：任何使用 WATCH/MULTI/EXEC 事务写的业务。HSET/LPUSH/ZADD 等多参数命令经事务执行后重启回放 AIOOBE（RuntimeException 不被 catch）→ 启动失败；单参数 PUT 则值被静默污染；LPUSH 的 `Object[]{V[]}` 经 `toString()` 得到 `[Ljava.lang.Object;@1a2b3c` 垃圾字符串落盘。
- **根因**：事务 AOF 走了 `log(String, String, String)` 文本拼接旧通道，而非 `logTyped(op, key, Object...)` 类型化通道，参数结构被压扁。
- **修复**：exec 改为 `aofService.logTyped(cmd.aofOp, cmd.aofKey, cmd.aofArgsArray)`（QueuedCommand 保存 `Object[]` 原数组而非拼接串）；删除或废弃文本拼接通道。

#### 缓存-3：AOF 重写换文件存在数据丢失竞态窗口

**位置**：`AofService.java:750-772`（doRewrite）

```java
synchronized (rewriteBuffer) { /* 第二次排空 */ rewriteBuffer.clear(); }  // 750-756
out.flush(); tmpFos.getFD().sync();
synchronized (writeLock) {          // 760 —— 与上面排空之间存在窗口
    aofDataOut.close();
    Files.move(tmpFile → aofFile, REPLACE_EXISTING);  // 旧文件被覆盖
}
```

- **触发场景（高并发写 + 自动重写）**："第二次排空 rewriteBuffer 结束"到"获取 writeLock"之间到达的写命令：既写入旧文件（随后被 `Files.move` 覆盖丢弃），又进入 rewriteBuffer（此后再无人排空，下次 `startRewrite()` 直接 clear）→ 该批命令持久化丢失，重启后数据回退。
- **根因**：此前为缩短写锁持有时间把缓冲排空移出 writeLock，破坏了"排空→换文件"的原子性。
- **修复**：将最后一次 rewriteBuffer 排空移入 `synchronized (writeLock)` 块内、换文件之前执行；或引入状态标记使换文件期间写命令只进 buffer 不进旧流。

### 1.2 P1 严重

#### 缓存-4：fsync 永不生效：always/everysec 实际退化为 no 【已复核】

**位置**：`AofService.java:361-367` + 流包装 `AofService.java:122`

```java
aofOut = new BufferedOutputStream(new FileOutputStream(aofFile, true), ...);  // 122
...
private void flushToDisk(boolean forceFsync) throws IOException {
    aofDataOut.flush();
    if (forceFsync && aofOut instanceof FileOutputStream) {  // ← 恒为 false！
        ((FileOutputStream) aofOut).getFD().sync();
    }
}
```

- **触发场景**：所有开启 AOF 的部署。`appendfsync=always` 用户以为每次写都落盘，实际只 flush 到 OS page cache；机器掉电/OS 崩溃丢失全部未落盘数据。everysec 的每秒 fsync 同样从未执行。
- **根因**：instanceof 检查的是被装饰器包装后的外层流，类型判断写错对象。
- **修复**：字段保留 `FileOutputStream` 原始引用并对其 `getFD().sync()`；或改用 `FileChannel.force()`。

#### 缓存-5：AOF 回放读取 CRC 但从不校验，损坏记录被静默应用

**位置**：`AofService.java:437`

```java
in.readInt(); // stored CRC —— 读出即丢弃
```

- **触发场景（海量数据）**：磁盘位翻转、torn write（写一半进程崩溃）。损坏的 value/命令被当作合法数据回放进内存，数据损坏且无感知。与 `encodeCommand()`（312-320 行）认真计算 CRC32 形成讽刺对比。
- **修复**：回放时重算 CRC 与存储值比对，不匹配则按 corrupted 处理（截断后续回放并告警）。

#### 缓存-6：PUT_EXPIRED 回放用相对 TTL 重建，重启等于"续期"

**位置**：`AofService.java:469-473` + `CacheEntry.java:17`

- **触发场景（海量短 TTL 数据 + 频繁重启/滚动升级）**：回放 `cache.put(key, v, ttl)` → `expireTime = now + ttl`（ttl 是写入时的原始值）。1 小时 TTL 的 key 在第 59 分钟重启后又获得完整 1 小时；反复重启则永不过期 → 内存堆积、业务看到"幽灵数据"。
- **根因**：AOF 格式存相对 TTL 而非绝对过期时间戳（Redis 用 PEXPIREAT 解决）。
- **修复**：OP_PUT_EXPIRED 改存绝对过期时间戳，回放精确恢复。

#### 缓存-7：容器类型（Hash/List/Set/ZSet）TTL 完全不持久化，重启后永不过期

**位置**：`SimpleCache.java:133-144`（`expire()` 不记 AOF）；`AofService.java:813-875`（四类容器重写均不写 TTL）；迁移导入依赖 `CacheCapability.java:366-394` 调 `c.expire(...)`

- **触发场景（海量数据 + 容器带 TTL）**：重写后所有容器 TTL 永久丢失；迁移导入的容器 TTL 同样不落盘。容器只增不减 → 内存泄漏。
- **根因**：AOF 操作集缺少"EXPIRE"类命令，重写路径只对 plain KV 处理 TTL（writeKeyValueEntries:800-806）。
- **修复**：新增 OP_EXPIRE 命令；`expire()` 记 AOF；重写时对每个容器 key 追加 OP_EXPIRE。

#### 缓存-8：zsetMemberIndex 永不清理：ZSet key 删除/过期/LRU 淘汰后索引泄漏

**位置**：`SimpleCache.java:690`（定义）；`remove():374-385`、`removeEldestEntry():45-52`、`evictExpired():888-901`、`clear():388-404`、`doGet() 过期分支:362-367` —— 五处删除路径无一处清理

- **触发场景（海量 ZSet 高频增删，如排行榜按天滚动 key）**：每个被删的 zset key 留下一份完整 member→score 索引 → 堆持续增长 → OOM。
- **修复**：上述 5 处删除路径统一 `zsetMemberIndex.remove(key)`；`clear()` 加 `zsetMemberIndex.clear()`。

#### 缓存-9：缓存穿透防护（空值缓存）完全失效：loader 每次都被调用

**位置**：`SimpleCache.java:322-349`（getWithLoader）+ `doGet():369-370`

```java
// doGet 末尾：NULL_MARKER 在返回前就被解包成 null
return value == NULL_MARKER ? null : value;
// getWithLoader: V cached = doGet(key); if (cached != null) ... → 永远为 null → 永远走 loader
```

- **触发场景（高并发查询不存在的 key，穿透攻击/爬虫）**：`NULL_MARKER` 虽被写入（340 行），但 `doGet` 提前解包使 getWithLoader 永远观察不到 → 每个请求打到后端 loader（通常是 DB）→ 后端被打爆。`unwrapNullMarker()` 成为死代码。
- **修复**：doGet 返回原始值（含 marker），由 `get()` 与 `getWithLoader()` 各自决定解包时机。

#### 缓存-10：WATCH → MULTI 标准顺序下乐观锁静默失效

**位置**：`SimpleCache.java:801-807`（multi）vs `869-881`（watch）

```java
public void multi() {
    txHolder.remove();   // 把 watch() 刚存入的 watchedKeys/watchedVersions 一并丢弃
    TxContext<K> tx = new TxContext<>();  // watchedKeys 为空
    ...
}
```

- **触发场景（高并发）**：类 Redis 标准用法 WATCH→MULTI→EXEC。exec 冲突检查（834-840 行）遍历空集合 → 永不中止 → 并发丢失更新且无任何报错。
- **根因**：multi() 为修复"旧事务残留"直接 remove ThreadLocal，误伤 watch 前置状态。
- **修复**：multi() 保留已有 tx 的 watchedKeys/watchedVersions，仅重置 commands 与 active 标志。

#### 缓存-11：同组并发 XREADGROUP ">" 重复投递 + PEL 所有权错乱

**位置**：`StreamStore.java:498-554`（readNewForGroup/readAfterForGroup 全程无锁）

```java
// 读 tailMap → 写 PEL → advanceLastDelivered，三步非原子
group.getPel().put(id, pel); consumer.addPending(id); group.advanceLastDelivered(id);
```

- **触发场景（高并发同组多 consumer）**：两线程读到同一 lastDeliveredId、各自把同一批消息投递给不同 consumer → 同一消息被消费两次；PEL.put 互相覆盖导致 XACK 从错误 consumer 移除 pending。Redis 语义是同组一条消息仅投递一个 consumer。
- **根因**：只有 `advanceLastDelivered` 是 synchronized（ConsumerGroup.java:61），读-改-写整体无互斥。
- **修复**：readNewForGroup 全程 `synchronized (group)`（或与 xadd 同一把 per-stream 锁）。

#### 缓存-12：AOF 重写期间 rewriteBuffer 无界增长 → OOM

**位置**：`AofService.java:96`（`List<byte[]> rewriteBuffer`）+ `330-334`（重写期间每条命令入内存 buffer）

- **触发场景（海量数据 + 高并发写）**：重写耗时分钟级，期间所有写命令字节在堆内累积，无上限无背压 → OOM；OOM 又导致重写失败 → 恶性循环。
- **根因**：Redis 用 fork COW 规避，本实现进程内重写却未给 buffer 设上限。
- **修复**：buffer 超阈值溢出到临时文件；或背压暂停新写；或分段重写缩短窗口。

#### 缓存-13：Codec 字符串编码用 writeShort 限长 64KB，大 value 静默截断损坏

**位置**：`Codec.java:70-72`（`out.writeShort(utf.length)`）+ `144-147`（readUnsignedShort）

- **触发场景（大 value >65535 字节）**：长度被截断为低 16 位，解码按错误长度读取 → 值被静默截断，调用方拿到残缺数据无任何异常。非 Serializable 兜底分支（120-123）同病。注意 `CacheChunkCodec.encodeValue` 用 writeUTF（超限响亮失败），两处行为不一致。
- **修复**：改用 writeInt 长度前缀（同步升级格式版本）；写入前显式校验。

#### 缓存-14：反序列化黑名单在 readObject 之后检查，形同虚设；gRPC plaintext 无认证

**位置**：`Codec.java:187-193`

```java
Object obj = ois.readObject();   // gadget 链在此已执行完毕
if (obj != null && BLOCKED_CLASSES.contains(obj.getClass().getName())) { ... } // 为时已晚
```

- **触发场景（安全）**：任何能访问 gRPC 数据面端口者（`CacheGrpcClient.java:177-179` usePlaintext、无认证），通过 forwardPut 投递恶意序列化字节 → RCE。黑名单只拦"顶层对象恰好是 gadget 类"的幼稚 payload。
- **修复**：使用 `ObjectInputFilter`（JEP 290）白名单制；gRPC 通道加 mTLS/认证。

#### 缓存-15：exportPartition 全量物化分区数据，大分区迁移直接 OOM

**位置**：`CacheCapability.java:280-332`

- **触发场景（海量数据下的分区迁移/扩缩容）**：`new LinkedHashMap<>(e.getValue())`、`new ArrayList<>(...)`、ZSet 全量展开、Stream 全量快照——整个分区在堆内复制一份。10GB 分区 → 源节点额外占 10GB+ 堆 → OOM。`CachePartitionAdapter.java:42` 注释自称"分片不再整体物化"，但上游 exportPartition 早已物化完毕。
- **修复**：exportPartition 改为返回 `Iterator<CachePartitionEntry>`，逐条编码逐条发送。

#### 缓存-16：内存实际无界：maxSize 只限 key 个数，值大小/Stream 数量/PEL 均无界

**位置**：`SimpleCache.java:66`（`DEFAULT_MAX_SIZE = 100_000`）、`CacheCapability.java:98`（`new SimpleCache<>()` 默认构造，无配置入口）；`StreamStore.java:39`（streams map 无上限）、`ConsumerGroup.java:24`（pel 无上限）

- **触发场景（海量数据）**：10 万个 key 每个挂 100MB List → 10TB 堆；百万个 stream key、消费者不 ACK 时 PEL 无限增长 → OOM。`DEFAULT_MAX_STREAM_LEN=100 万/流` 的防 OOM 声明在流数量无界面前无意义。
- **根因**：淘汰维度是"条目数"而非"字节数"，子系统（Stream/PEL/zsetMemberIndex）游离于淘汰体系外。
- **修复**：引入基于字节水位的淘汰；maxSize/流上限/PEL 上限可配置；PEL 超阈值告警 + XAUTOCLAIM 强制回收。

#### 缓存-17：集群 fan-out 与 Stream 唤醒共用 ForkJoinPool.commonPool 跑阻塞调用

**位置**：`CacheGateway.java:176,213`（`CompletableFuture.supplyAsync` 未指定 executor，gRPC 阻塞调用最长 30s deadline）；`StreamStore.java:135`（runAsync 唤醒 waiter）

- **触发场景（大规模集群 + 慢/宕节点）**：listKeys/countKeys fan-out 把 commonPool（大小≈核数-1，全 JVM 共享）占满 30 秒 → 同 JVM 所有 commonPool 任务饿死，包括 StreamStore 的 XADD 唤醒（阻塞读全部超时）→ 级联故障。
- **修复**：为 fan-out 与唤醒分别建独立有界线程池，对 future.join 加超时。

## 2. 集群调度模块（21 项）

### 2.1 P1 严重

#### 调度-1：Membership 全网状心跳协议 O(N²)：全量视图 ack + 每心跳一次 DB 自查询 【已复核】

**位置**：`MembershipService.java:248-285`（heartbeatTick 对每个 peer 发心跳）、`235-242`（buildAck 携带全量视图）、`202-212`（每收到一条心跳即 buildAck）

```java
private HeartbeatAck buildAck() {
    refreshSelf();                       // → registry.get(self) → DB 查询
    HeartbeatAck.Builder builder = HeartAck.newBuilder();
    for (NodeInfo info : view.values()) { builder.addMembers(toProto(info)); }  // 全量 N 个成员
    return builder.build();
}
```

- **触发场景（大规模）**：协议为全网状——每节点每周期向 N-1 个 peer 各发心跳，每条心跳换回含全部 N 个成员的 ack。N=1000、interval=1s：
  - 每节点每秒收 ~1000 个 ack × ~100KB ≈ **100MB/s 入站带宽/节点**；
  - 每节点每秒 ~1000 次 `refreshSelf()` → `registry.get(self)` 点查，全集群 **~10⁶ qps 打到共享 PG**；
  - 每节点维持 N-1 个 ManagedChannel + N-1 个入站流；
  - 所有出站心跳在**单线程** heartbeatExecutor 上串行派发（129 行），tick 耗时随 N 线性增长，挤压故障检测时效。
- 几百节点即接近网络/DB 上限，千节点级完全不可行。
- **根因**：把「全量视图同步」嵌进每一对心跳请求-应答，无版本号/增量机制；自身信息不缓存。
- **修复**：改 gossip 抽样（每周期随机 k 个 peer push-pull）+ 视图版本号增量同步；selfInfo 本地缓存；心跳独立小线程池。

#### 调度-2：故障检测 DEAD 判定无回滚路径：任何 >6s 的抖动会把健康节点永久逐出 【已复核】

**位置**：`MembershipService.java:359-372`（判 DEAD 且明确不复活）、`402-407`（merge 复活路径排除 DEAD）、`254-260`（directory 异常 → 空 peers）；`NodeStateMachine.java:36`；`NodeRuntime.java:82-116`

```java
// merge():
recoveredToActive = incoming.state() == NodeState.ACTIVE
        && local.state() != NodeState.ACTIVE
        && local.state() != NodeState.DEAD;   // ← 本地视图曾为 DEAD 则不回写注册表
```

- **触发场景（长期运行/高并发）**：默认 `deadAfterMisses=6 × 1000ms = 6s`。任一节点一次 >6s 停顿（长 GC、网卡闪断、瞬时网络分区、DB 抖动导致 `directory.peers()` 异常 → 全集群互停心跳）即被所有 observer 判 DEAD：
  1. `stateSink.apply → registry.markState(DEAD)` 落库成功；
  2. 节点恢复后心跳直报，视图可自愈为 ACTIVE，但 `recoveredToActive` 明确排除 local=DEAD，注册表永不回滚；
  3. `NodeStateMachine` 规定复活必须重走 register，而 `NodeRuntime` 运行期没有任何重注册逻辑，管理端点也无 revive 接口。
- 后果：健康节点被永久排除出 `listAlive()` → 调度器把其分区治愈迁走（迁移风暴），容量永久损失，**只能重启进程恢复**。
- **根因**：DEAD 被设计为注册表终态，却没有配套的「重新注册触发器」；故障检测与成员资格之间没有宽限/复核机制。
- **修复**：直报复活时允许带 epoch 递增的 DEAD→JOINING 回写；或 NodeRuntime 监听自身被标 DEAD 后自动重注册；DEAD 判定增加二次确认。

#### 调度-3：放置计算 O(P×N) MD5，ReconcileLoop 每周期、每能力类型重复全量重算

**位置**：`WeightedRendezvousHash.java:52-71,94-95,128-132`；`PlacementEngine.java:67-69`；`ReconcileLoop.java:436-437,451-452,505-506,700-701`

```java
// selectNodes —— 每个分区对每个节点算一次 MD5
for (int i = 0; i < nodes.size(); i++) { scores[i] = computeWeightedScore(input, nodes.get(i)); }
...
long hash = hash(input + ":" + node.nodeKey());   // 每次哈希都做字符串拼接 + getBytes
```

- **触发场景（大规模）**：单次 compute = P×N 次 MD5 + P×N 次字符串拼接 + 每分区 `double[N]`/`boolean[N]` 分配 + O(P×N×rf) top-N 扫描。`reconcile(type)` 在**稳态**下每周期也全量 `computePrimaries`；排空/治愈/重平衡路径单周期最多 2 次全量 compute。以 10k 分区 × 1000 节点 × 3 能力类型估算：每周期 ~10⁸ 次 MD5，单线程耗时数十秒级，**远超 10s 租约 TTL** → 每周期失租 → leader 走马灯，调度停摆。无任何结果缓存。
- **修复**：以（节点集哈希, P, rf）为键缓存 compute 结果；MD5 换 xxHash/Murmur3；nodeKey 预编码复用；分区维度并行。

#### 调度-4：阻塞式命令扇出跑在 ForkJoinPool.commonPool，join() 无超时，命令阶段不续租

**位置**：`ReconcileLoop.java:329-341`（start 扇出）、`349-355`（freeze 扇出）、`572-583`（stopNodes）；`GrpcNodeCommandChannel.java:36`（5s deadline）；`LocalNodeCommandChannel.java:51-53`

```java

        .map(node -> CompletableFuture.supplyAsync(() -> commands.startCapability(node, type)))  // 无 executor → commonPool
        .toList();
for (...) { if (startFutures.get(i).join()) { ... } }   // 无超时
```

- **触发场景（大规模 + 高并发）**：对 500 个节点下发命令，若大面积不可达每个耗满 5s：500×5s/(核数-1) ≈ 数百秒，期间 commonPool 被占满（全 JVM 其他并行任务饥饿），且命令阶段无续约 → 必然失租 + 新旧 leader 并发动作。`node==self` 时走本地 `convergeStop` 同步执行 drain()+stop() 钩子**无任何超时**：单钩子挂死即钉死调谐线程。
- **修复**：专用有界线程池 + orTimeout；命令阶段分批并在批间续租；本地 convergeStop 放独立线程加超时熔断。

#### 调度-5：缩容排空失败后若管理员重新启用 desired，freeze(true) 永久锁死

**位置**：`ReconcileLoop.java:349-355`（freeze 结果被丢弃）、`400-404`（失败保持冻结）、`560-562`（解冻只存在于成功路径）

```java
    LOG.warn("... keep nodes frozen and retry after cooldown", ...);   // 失败 → 永久保持冻结

```

- **触发场景**：节点 X 排空中迁移持续失败 → 管理员放弃缩容、desired 改回 ACTIVE：X 不再属于 toStop，任何路径都不会再触碰它；X 的能力仍处于冻结态，**未迁走分区的写入被静默拒绝**。全代码无路径补发 freeze(false)，只能重启节点解除。
- **根因**：冻结不是期望态的一部分，reconcile 无从感知偏差。
- **修复**：每周期对 `actualOn ∩ desiredOn` 节点主动下发幂等 `freeze(false)`；或给冻结加租约/超时自动解除。

## 3. 存储模块（27 项）

### 3.1 P0 致命

#### 存储-1：迁移导入端整对象堆内聚合，大对象/并发迁移直接 OOM

**位置**：`StorageCapability.java:84,575-588`

```java
private final Map<String, ByteArrayOutputStream> importBuffers = new ConcurrentHashMap<>();
...
ByteArrayOutputStream buf = importBuffers.computeIfAbsent(aggKey, k -> new ByteArrayOutputStream());
buf.write(chunk.data(), 0, chunk.data().length);
if (chunk.fin()) { byte[] all = buf.toByteArray(); ... }
```

- **触发场景（海量数据）**：单对象上限默认 1GB。迁移一个近 1GB 对象：ByteArrayOutputStream 扩容峰值 ~2 倍 + `toByteArray()` 再完整拷贝一份 ≈ **单对象瞬时 3GB 堆**；多分区/多对象并发导入叠加 → 节点 OOM。且迁移中途失败时 importBuffers 条目不清理（仅 fin/偏移错误时移除），还是内存泄漏源。导出端特意做了惰性流式（422-428 行注释明确警示），导入端完全违背。
- **修复**：导入端落盘流式化——分片直接追加写本地临时文件，fin 片到达后走 `putReplica`；对聚合数量与总字节做硬上限；为中断聚合增加超时清理。

#### 存储-2：IngestObserver：落盘线程提前退出后 push() 无限阻塞，gRPC 回调线程永久泄漏

**位置**：`StorageGrpcServer.java:245-263,312-319`

```java
void push(byte[] data) {
    queue.put(data);          // 队满无限阻塞，无人会 interrupt
...
input.push(chunk.getData().toByteArray());
```

- **触发场景（高并发）**：任何让落盘线程提前结束的情形——磁盘满（writeObject 抛 IOException）、frozen、超大小（SizeLimitedInputStream 中途抛出）、以及**副本幂等跳过**（putReplica 发现既有版本 ≥ 来的版本直接返回而不消费输入流，ObjectStore.java:238-240；这正是对账重试/迁移重放的常态路径）。线程退出后队列（容量 8）填满，`onNext` 里 `queue.put` 永久阻塞；gRPC 的 `onError`/cancel 排在 `onNext` 之后串行投递，永远送不达。磁盘满时所有在途大上传批量命中 → gRPC executor 线程逐个钉死 → **整节点 RPC 不可用**。副本路径下服务端提前应答、客户端视为成功继续发送，服务端同样卡死。
- **根因**：生产者（gRPC 回调）与消费者（落盘线程）生命周期未联动；工作线程退出不 `fail()`/清空队列；push 无超时。
- **修复**：增加 workerDone/failed 状态，工作线程退出时置位并 `input.fail()`；onNext 先检查状态；push 改限时 offer。

#### 存储-3：元数据全量索引常驻堆内且无上限，启动全盘 JSON 扫描 【已复核】

**位置**：`ObjectStore.java:132-133,560-607`

```java
private final Map<Drive, ConcurrentHashMap<String, ConcurrentSkipListMap<String, ObjectMetadata>>> index
...
ObjectMetadata m = objectMapper.readValue(c, ObjectMetadata.class);  // 每对象一次文件读+JSON解析
```

- **触发场景（海量数据）**：索引无条件容纳**全部**对象。每条目 = SkipListMap 节点 + ObjectMetadata（key/etag/contentType 字符串 + 空 LinkedHashMap）≈ 400-600B，**1 亿对象 ≈ 40-60GB 堆**，OOM 不可避免。启动 `rebuildIndex()` 对每个 object.meta 读文件 + JSON 反序列化，亿级对象耗时以小时/天计，节点无法在合理时间内提供服务。
- **根因**：为让 list/count 变 O(log N + pageSize)，把"全量元数据常驻内存"当作前提，无容量上限、无淘汰、无持久化索引。
- **修复**：元数据下沉到嵌入式 KV（RocksDB 等）或按前缀分片索引 + 热点缓存；启动重建改为加载持久化索引快照 + 增量重放；至少先给索引加容量上限并降级为扫描。

## 4. 跨模块结构性问题（建议单独立项）

1. **"全量物化/全量索引"模式在三模块各自复现**：缓存 exportPartition（缓存-15）、存储内存索引（存储-3）、调度 primaries 全行加载（调度-P2#6）。海量数据下全部是 OOM/启动悬崖，需要统一的**流式迭代 + 分片 + 持久化索引**改造规范。
2. **阻塞调用普遍提交给 ForkJoinPool.commonPool**：缓存 fan-out（缓存-17）、调度命令扇出（调度-4）、Stream 唤醒（缓存-17）。一个慢点拖垮全 JVM 的所有异步任务。需要统一的**专用有界线程池规范**并禁止数据面使用 commonPool。
3. **持久化承诺系统性失效**：缓存 fsync 从未执行（缓存-4）、存储 meta/目录不 fsync（存储-13）、迁移完成即删源端（缓存-33）。三者叠加意味着**"迁移完成"不等于"数据安全"**，应建立端到端持久化确认（导入确认携带持久化位点后源端才可清理）。
4. **userMetadata 丢失出现在复制与迁移两条独立通道**（存储-7/8），说明搬迁协议缺少"全字段往返一致性"测试，建议补充协议级一致性测试（任意对象经复制/迁移后字节与元数据完全一致）。
5. **全链路缺 fencing/epoch**：已知报告缺陷 4（租约脑裂）之上，又发现租约时钟偏移（调度-14）、缓存数据面纪元校验架空（缓存-31）、存储副本同版本静默丢弃（存储-26）。建议作为统一专项：租约发放单调 epoch，所有命令/写入携带 epoch 并在存储层做单调校验。
6. **单机内存模型假设贯穿缓存与存储**：缓存无字节水位淘汰（缓存-16）、存储无背压（存储-2），在海量数据场景下节点是"要么全装下、要么 OOM"。需要容量规划接口（按字节配额 + 拒绝策略）替代当前静默增长。

## 5. 整改优先级建议

1. **P0 立即修复（数据安全/可用性悬崖）**：缓存-1（ZSet+AOF 重启必崩）→ 缓存-2（事务 AOF 损坏）→ 缓存-3（重写丢数据）→ 存储-2（IngestObserver 死锁拖垮整节点）→ 存储-1（迁移导入 OOM）→ 存储-3（元数据索引无界）。
2. **P1 第一批（持久化与正确性根基）**：缓存-4（fsync）与存储-13（fsync 缺口）合并为"持久化加固"专项；缓存-5/6/7（CRC/TTL）；调度-2（DEAD 不可逆）+ 调度-12/13（注册竞态/采样耦合）合并为"成员资格生命周期"专项；存储-5/6/15（错配对与版本分叉）合并为"读写原子性"专项。
3. **P1 第二批（规模化悬崖）**：调度-1（O(N²) 心跳）与调度-3（O(P×N) 放置）决定系统规模上限，建议先做放置缓存（收益最大、改动最小），心跳协议改造随后；调度-4/5（命令扇出与冻结锁死）；存储-14（对账风暴）。
4. **安全专项**：缓存-14（反序列化 RCE 面）建议独立走安全流程，优先级不依赖其他项。
5. **验收基线**：缓存建议补"重写→重启→回放"混沌测试（覆盖 ZSet/事务/容器 TTL）；存储建议补"磁盘满 + 并发上传 + 副本重放"故障注入测试；调度建议以 1000 节点影子集群验证心跳带宽与放置计算耗时回归指标。

> 注：本报告中缓存-1/4、调度-1/2、存储-3 等关键条目已由第二审查人对照源码逐行复核，代码位置与结论一致。
