## 0. 核心原则：五大架构特性

### 0.1 特性定义与验收指向

| # | 特性 | 定义 | 当前短板（对应条目） | 验收指向 |
|---|------|------|----------------------|----------|

| ② | **集群动态调度** | Desired→Actual 持续收敛：故障自愈、副本提升、冻结/解冻、能力生命周期灵活可控 | 治愈/冻结/解冻补偿缺口（S5）、状态回写竞态（S12）、fencing 架空（C31）、DEAD 不可逆（S2） | 杀任意单节点 30s 内分区可用性恢复；冻结残留率 = 0；调度决策状态永不僵死 |

### 0.2 决策规则

1. **一致性优先**：修复方案与性能优化冲突时，先保正确性（先例：缓存-3 的 08-27 锁收窄优化引入了丢数据窗口，必须回补）。
2. **性能改进不得静默改变语义**：锁收窄、并行化、缓存化必须附带语义不变证明（测试锚点）。
3. **特性间冲突显式分阶段**：如 ④要求抽样心跳、②要求检测时效——先做不改变时序的增量优化，抽样改造以书面时延预算为前置。
4. **容量治理不静默丢数据**：超限策略是拒绝+告警，不是后台静默驱逐（除非业务显式开启）。
5. **可观测性随修复同行**：每个被修复的静默失败路径必须产出日志+指标（回放毒记录、损坏 meta、降级列举、冻结补偿等）。

### 3.2 AOF 重写子系统原子性（C3 + C12 + C36）——阶段 2

现状（已核验）：`doRewrite` 第二次排空在 `:750-758`（锁外），换文件在 `:760-772`（`writeLock` 内）；窗口内命令双写旧流+buffer，旧流随后被覆盖 → 丢失。该窗口由 08-27 锁收窄引入（`:749` 注释）。

**方案：`swapping` 状态机，排空+换文件合并为一段临界区，写路径零长锁回归**：

```java
private volatile boolean swapping;   // 换文件进行中

// writeCommand（:324）入口改造：
synchronized (writeLock) {
    if (swapping) {                          // 旧流即将作废：只进 buffer，绝不写旧流
        synchronized (rewriteBuffer) { rewriteBuffer.add(cmdBytes); }
        return;                              // flush 语义由换文件后的新流承接
    }
    aofDataOut.write(cmdBytes); ...（现有逻辑：计数/入 buffer/按策略 flush）
}

// doRewrite 尾部（替换 :749-772）：
synchronized (writeLock) { swapping = true; }          // ① 冻结旧流写入
try {
    synchronized (writeLock) {                          // ② 排空 + 换文件一段完成
        synchronized (rewriteBuffer) {
            for (byte[] cmd : rewriteBuffer) out.write(cmd);
            rewriteBuffer.clear();
        }
        out.flush(); tmpFos.getFD().sync();
        aofDataOut.close();
        Files.move(tmpFile.toPath(), aofFile.toPath(), REPLACE_EXISTING, ATOMIC_MOVE);
        aofRawOut = new FileOutputStream(aofFile, true);   // C4：保留原始引用
        aofOut = new BufferedOutputStream(aofRawOut, properties.getBufferSize());
        aofDataOut = new DataOutputStream(aofOut);
        aofFileSize = aofFile.length();
    }
} finally { synchronized (writeLock) { swapping = false; } }
```

性能不变量：②的排空量受 C12 上限约束（有界），临界区时长 = 排空写盘 + 两次系统调用，与现状同量级；写路径在 rewriting 常态期仍走窄锁。
C12：`rewriteBuffer` 字节上限（配置，默认 256MB）；超限 → `swapping` 复位、删 tmp、中止本次重写 + 告警，下个周期重来。
C36：`stop()` 等待在途重写终结（join 超时后置位禁止 swap 再关流）。
**验收**：N 线程并发写 + 自动重写 + 随机时刻杀进程，重启回放条数 = 最后一致点写入条数（中间命令不得蒸发）。

### 3.7 IngestObserver 生命周期（T2）——阶段 1

现状（已核验 `StorageGrpcServer.java:244-340`）：worker 经 `workers.submit` 运行 `sink.ingest`；数据片 `push` 用 `queue.put` **无限阻塞**（仅哨兵限时）；任何让落盘线程提前结束的路径（磁盘满/超限/**副本幂等跳过不消费流**）都会钉死 gRPC 回调线程。

```java
private volatile boolean workerGone;          // 新增

worker = workers.submit(() -> {
    try {
        ObjectMetadata meta = sink.ingest(header, input);
        response.onNext(toProto(header.bucket, meta));
        response.onCompleted();
    } catch (Throwable t) {
        response.onError(asStatus("ingest", t));
    } finally {
        workerGone = true;                    // 任何退出路径置位
        input.fail();                         // 唤醒可能的读阻塞
    }
});

void push(byte[] data) {                      // 替换 :312-319
    if (workerGone) {
        throw new UncheckedIOException(new IOException("ingest worker already exited"));
    }
    try {
        if (!queue.offer(data, INGEST_POLL_TIMEOUT_MS, TimeUnit.MILLISECONDS)) {
            throw new UncheckedIOException(new IOException("ingest queue full (consumer gone)"));
        }
    } catch (InterruptedException e) { Thread.currentThread().interrupt(); throw ...; }
}

// onNext：捕获 UncheckedIOException → 该流判死（客户端已收到成功/错误应答的场景下，
// 后续分片安全丢弃；未应答场景回 onError），gRPC 回调线程不再钉死
```
语义核对：副本幂等跳过 = 服务端提前应答成功 + 丢弃后续冗余分片，与"重放安全"一致；磁盘满 = worker 异常退出 + onError，客户端感知失败。
**验收**：磁盘满注入、副本重放注入下，节点全部 RPC 保持可用（健康检查 + 无关请求通过）。

### 3.12 成员资格生命周期专项（S2 + S12 + 深审6遗留）——阶段 5

设计约束（既有实现 + 既往教训）：复活必须经 register（epoch 重置）；直证自报无条件采纳；同态回写跳过。

```java
// ① NodeRuntime 自动重注册（新增方法，:83-85 的 started 守卫不拦此路径）：
public synchronized void reRegister() {
    // 触发条件：自身被标 DEAD 且 desired=ACTIVE；心跳线程已在运行，直报即复活通路
    ResourceSnapshot snapshot = monitor.snapshot();
    registry.register(NodeInfo.of(self, host, grpcPort(),
            NodeState.JOINING, 0L, weight, snapshot));     // register 重置 epoch（合法复活）
    // 自检通过后：
    registry.markState(self, NodeState.ACTIVE);
}
// 自我监测：周期（每 5×心跳间隔）查 registry.get(self)；发现 DEAD 且进程健康 → reRegister()
// ② 管理端点：POST /rt/nodes/{id}/revive（人工触发，语义同上）
// ③ JOINING 超时：成员服务对 >2×心跳间隔 无心跳的 JOINING 节点自动 tombstone（兜底启动孤儿）
// ④ 深审6遗留：start() 失败 catch 内 registry.tombstone(self)（异常继续上抛）；
//    RuntimeBootstrapper 启动失败路径补清理（当前 :195 直接抛、:256 stop() 因 running=false 不清理）
// ⑤ S12：stateSink 回写比较 stateEpoch（低于注册表当前值拒绝）；
//    豁免：直证自报 + register 重置；慢启动保护：注册后 deadTimeoutMs 宽限期内不判 DEAD
```
**验收**：注入 8s GC 停顿 → 判 DEAD → 恢复后 30s 内自动回 ACTIVE，无状态机异常刷屏；端口占用启动失败 → 无 JOINING 残留；复活后 state_epoch 重置（断言）。

## 6. 特性验收基线与度量

### 6.1 回归测试恢复（阶段 5 完成）

深审 6 个确定性复现测试全部重建入树（内存仓库 + TestClock，无外部依赖）：缺陷 1/3 断言修复后行为；2/5 断言幂等收敛与钩子单次执行；4 反转断言"不出现双 leader"；6 断言无孤儿。纳入 CI 作为调度语义的永久防线。

### 6.2 混沌与故障注入（阶段 1/2 起持续）

| 场景 | 覆盖条目 | 通过标准 |
|------|----------|----------|
| 并发写 + 自动重写 + 随机时刻杀进程 | C3/C12 | 重启回放条数 = 最后一致点 |
| 重写→重启→回放（ZSet/事务/容器 TTL/大 value） | C1/C2/C6/C7 | 数据 100% 恢复，无毒记录崩溃 |
| 磁盘满 + 并发上传 + 副本幂等重放 | T2/T12 | 节点全部 RPC 可用 |
| 覆盖写/删桶中途崩溃 | T5/T10 | 无错配对、无跨节点分叉 |
| 杀 leader + 杀数据节点 + DB 抖动 | 深审4/缺陷3 | 接管 ≤2×TTL，治愈完成 |
