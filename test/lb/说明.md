# ww LB 负载均衡压测脚本（/cache/lb-echo 回显探针）

基于 **JMeter 5.6.3** 的 `.jmx` 脚本，对 runtime-server 内置反向代理 LB 做分发正确性与吞吐压测。
配套后端探针 **`GET /cache/lb-echo`**：免鉴权、零业务依赖，返回**实际处理请求的节点身份**，
压测工具据此统计流量在各后端节点间的分布是否均衡。

## 1. 回显接口说明

| 项 | 值 |
| --- | --- |
| 方法/路径 | `GET /cache/lb-echo` |
| 鉴权 | **无**（SecurityConfig GET 白名单，与 `/rt/health` 同类探针；响应不含任何业务数据） |
| 依赖 | 无——CACHE/STORAGE 能力未 ACTIVE 也可压测纯转发链路 |
| 为何挂 `/cache` | LB 出厂默认代理前缀即含 `/cache/**`，无需改 LB 配置即可被反代；精确路径优先于 `/cache/{key}` |

响应示例（入口节点本机处理时 `forwarded=false`；经反代落到后端节点时为 `true`）：

```json
{"nodeId":"node-2","host":"10.0.0.2","httpPort":8082,"grpcPort":9102,"forwarded":true,"timestampMillis":1792071795800}
```

> 经 LB 转发后，响应头还带 `X-RT-LB-Target: <nodeId>`（由 `LbProxyFilter.writeResponse` 写入），可作为第二种分布判定来源。

## 2. 文件清单

| 文件 | 说明 |
| --- | --- |
| `lb-loadtest.jmx` | JMeter 测试计划（JMeter 5.6.3，GUI/非 GUI 均可） |

## 3. 前置：多节点集群与 LB 启用

1. 启动 ≥2 个 runtime-server 节点（不同 `SERVER_PORT` / `RUNTIME_NODE_ID`，共享同一 PostgreSQL 注册表；memory 模式注册表不跨进程，**不能用于多节点 LB 验证**）。
2. 等各节点在管理面为 ACTIVE（`GET /rt/status` 的 members）。
3. 启用 LB（默认关闭）。先登录拿 Bearer token，再读取当前版本并 PUT：

```bash
# 1) 登录（默认 admin/admin123，以实际部署为准）
TOKEN=$(curl -s -X POST http://127.0.0.1:8081/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"admin123"}' | python -c "import sys,json;print(json.load(sys.stdin)['token'])")

# 2) 开启 LB：入口=node-1、轮询、入口自身参与、代理 /cache/**（version 传 GET 回来的当前版本，首次为 0）
curl -s -X PUT http://127.0.0.1:8081/rt/lb/config \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"enabled":true,"entryNodeId":"node-1","strategy":"ROUND_ROBIN","selfServe":true,
       "pathPrefixes":["/cache/**","/storage/**"],"weightOverrides":{},
       "configRefreshMs":3000,"nodeViewRefreshMs":1000,"connectTimeoutMs":3000,
       "requestTimeoutMs":3600000,"version":0}'
```

> LB 未启用时脚本仍可执行，所有请求直接由入口本机处理（分布中只有入口节点），可用于压测入口自身性能。
> 验证反代分发必须 `enabled=true` 且请求打在 `entryNodeId` 节点上。
> 权重策略：`strategy=WEIGHTED` 后可用 `weightOverrides` 调各节点比例（如 `{"node-1":1,"node-2":3}` ≈ 1:3）。

## 4. 执行

### 非 GUI（推荐压测方式）

```powershell
# Windows PowerShell；-J 参数请整体加引号（PowerShell 调 .bat 的参数拆分坑）
& "E:\apache-jmeter-5.6.3\bin\jmeter.bat" -n -t test\lb\lb-loadtest.jmx `
  "-Jentry.host=127.0.0.1" "-Jentry.port=8081" `
  "-Jthreads=100" "-Jrampup=10" "-Jduration=60" `
  -l test\lb\result.jtl -e -o test\lb\html-report
```

### GUI（调试/观察）

双击 `bin\jmeter.bat` → 打开 `test\lb\lb-loadtest.jmx` → 在「用户定义的变量」里改入口地址/并发/时长 → 启动。
「查看结果树」监听器默认禁用（压测时不要开，极耗内存），需要调试时手动启用。

### 参数（全部可用 -J 覆盖，缺省即 GUI 中默认值）

| -J 属性 | 默认 | 说明 |
| --- | --- | --- |
| `entry.host` / `entry.port` | `127.0.0.1` / `8081` | **LB 入口节点**地址（不是任意节点；非入口节点不代理） |
| `threads` | `50` | 并发线程数 |
| `rampup` | `10` | 爬坡秒数（全部线程拉起时间） |
| `duration` | `60` | 持续施压秒数（线程组为「永远循环 + 调度器 duration」） |

请求超时固定 5000ms（connect/response，写死在采样器中——JMeter 加载期会把 `intProp` 解析成整数，不支持变量函数）。

## 5. 如何判定 LB 分布是否正确

脚本内置两层分布统计，**无需自己数日志**：

1. **聚合报告/汇总报告按后端节点分组**：JSR223 后置处理器用 JSON Extractor 取响应 `$.nodeId`，
   把取样器标签改写为 `lb-echo @ <nodeId>`。GUI 聚合报告中每个节点一行；
   非 GUI 生成的 HTML 报告（`html-report/index.html`）Statistics 表同样按节点分组，
   直接对比各节点样本数占比（ROUND_ROBIN 下应接近 1:1，WEIGHTED 下接近权重比）。
2. **jmeter.log 的 LB-DIST 行**：tearDown 线程组输出文本汇总，示例：

```
LB-DIST node=node-1 hits=1102
LB-DIST node=node-2 hits=1098
LB-DIST node=node-3 hits=1114
LB-DIST TOTAL=3314 (节点数=3)
```

判定要点：
- **分布均衡性**：各节点 hits 占比 ≈ 策略预期；某节点为 0 → 检查其是否 ACTIVE、httpPort 是否上报、`X-RT-LB-Forwarded` 防环头是否被中间设备污染；
- **错误率**：断言 HTTP 200，503=无 ACTIVE 后端、502=转发失败、连接拒绝=入口地址/端口错误；
- **延迟**：本机处理（`forwarded=false`）与转发（`forwarded=true`，多一跳 JDK HttpClient）的延迟差即 LB 转发开销，可在 JTL 中按 label 对比。

## 6. 已完成的本机冒烟验证

单节点（memory 模式，LB 关闭）非 GUI 冒烟：2 线程/4 秒 → 3314 请求、**0 错误**、777 req/s、平均 1ms，
`LB-DIST node=node-1 hits=3313`，HTML 报告正常生成。多节点真实分发需按第 3 节准备 PostgreSQL 共享注册表集群。
